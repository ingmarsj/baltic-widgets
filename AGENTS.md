# Contributor instructions

- Before continuing name-day work, read [NAMEDAYS_TASKS.md](NAMEDAYS_TASKS.md) for the active priority, completed work, saved source locations and continuation checks. Use its local-exact-namesake queue for people work and the separate history backlog for history verification. Keep this task entry point current after each batch; do not reconstruct status from chat history or restart already completed source runs.

- All documentation must be written and maintained in English only: READMEs, setup guides, API documentation, changelogs, and code documentation.
- Keep UI translations, generated horoscope texts, and locale-specific data multilingual. The English-only documentation rule does not apply to product content.
- Do not commit SQLite databases, raw archives, credentials, or private Home Assistant configuration. Publish generated public JSON through `data/`.
- Name-day source URLs belong in research files, documentation and provenance metadata only. Do not display source URLs, clickable citations or source lists in the widget interface. When reporting research progress, say that sources were recorded in working files; do not imply that links were added to the interface.
- Before name-day research, read [NAMEDAYS_SOURCES.md](NAMEDAYS_SOURCES.md). Extend that shared directory when a resource produces useful evidence, recording its exact page/section, supported claims and limits. Add source IDs and current verification outcomes to the next numeric round notes, update related documentation, and regenerate the backlog after content changes.
- Books and PDFs supplied by the user (for example from their Downloads folder) are registered with `nameday-source-cache.mjs index` into the private cache and are never committed.
- Never research the same source twice. Before searching the web, check [NAMEDAYS_SOURCE_INDEX.md](NAMEDAYS_SOURCE_INDEX.md) and search the private cache (`node scripts/nameday-source-cache.mjs search --query NAME --word true`). Download every new PDF or web page with `node scripts/nameday-source-cache.mjs fetch --url URL [--id ID --title TITLE]`, not curl or ad-hoc scripts: it reuses an already cached URL, stores the original and extracted text once in `../var/namedays-sources/`, and makes it searchable. Register a PDF already on disk with `index`. In Claude Code, a project hook also caches every WebFetch URL automatically and logs it to `../var/namedays-sources/fetch-log.jsonl`. When a source proves productive, give it a stable directory ID in NAMEDAYS_SOURCES.md (re-run `fetch`/`index` with that `--id` if it was cached under an automatic `WEB-*` ID) and record failed leads too, so they are not retried. `npm run backlog:namedays` regenerates the source index as well.
- Reuse the private page index for recurring PDF sources; follow [NAMEDAYS_PDF_CACHE.md](NAMEDAYS_PDF_CACHE.md). Index new reusable PDFs once by content hash, outside the public repository. Inspect original pages for exact spelling and record printed as well as PDF page numbers.
- Continue name-day priority research in the single shared branch `codex/namedays-round4`. Reuse this branch for subsequent rounds; do not create a branch per batch.
- Research name-day histories in calendar order. The widget shows only yesterday, today and tomorrow, so start with the nearest upcoming day in Priority 0 of `NAMEDAYS_BACKLOG.md` (regenerate it with `npm run backlog:namedays` before each round) and complete a research pass over that day's names in the LV, LT and EE calendars before moving to the next day. Use the bearer-count priority lists only after the upcoming days are covered.
- History reuse (LV since 13 November 2026; LT and EE since 16 November 2026, after the calendar pass): when a name has no history of its own and no explicit unverified hypothesis, the widget reuses the verified history of the same name written another way (diacritics or case) in the same calendar, or of the identical name in another calendar, opening with a one-line note. LV may borrow from LT and EE; LT and EE borrow only from their own calendar and from LV, never from each other, and for them a borrowed LV history keeps only its origin paragraph and is skipped when the explanation rests on Latvian material. Spelling-evidence notes and Lithuanian name-calendar histories are never reused.
- Where no local source can be found for a name (user decision, 16 November 2026), write a qualified hypothesis (“probably a form of …”, “may come from …”) instead of leaving the name without a history; keep documented facts below it and do not override reviewed or root histories.
- Widget history text never names dictionaries or other sources, and never presents a name as being of Russian origin (user decision, 16 November 2026, given the political climate): state the ultimate origin (Latin, Greek, Hebrew, …) and leave the name out when that is not certain.
- Refinement (user decision, 16 November 2026, round 163): do not call a name “Russian”, “Ukrainian” or “Belarusian” in widget text. Call modern forms East Slavic (or Slavic), tie historical ones to Kyivan Rus, and add the ultimate origin. Cognate lists and historical facts may still mention countries and languages. Early Soviet abbreviation names (Ninele, Vilens, Vilora, Kima, Revs, Rema, Marlens, Vladilena) are described as riddles that hint at their source without naming it. Coined and literary names show where they came from (book, place, coinage year). Ask the user with a full worked example before changing these wording rules again.
- Unverified name-history hypotheses may appear in the widget only with an explicit translated Hypothesis label and qualified wording. Keep their source basis, uncertainty and next verification step in the research notes and backlog, marked unverified. Do not count them as reviewed histories or silently promote proposed roots or spelling relationships into facts.
- A completed research pass may advance to the next calendar day with explicitly unverified hypotheses still open. Preserve those entries in the backlog and date queue for later verification; do not call the earlier day verified-complete. Process every unfinished name in all three calendars before advancing the research pass.

- Before writing or modifying horoscope content, read `HOROSCOPE_EDITORIAL_RULES.md`. Copy lives in `parsers/horoscope-text/<lang>.mjs` and is written natively in LV, RU, EN, LT and ET (never translated). Apply its Do/Avoid grammar, gender-neutral address, typography and non-mirroring rules in all languages and both moods, and run `node scripts/check-horoscope-text.mjs <lang> --samples`. Validate future provider output with `validateReading` before caching; bump the writer version and regenerate JSON after copy changes.
